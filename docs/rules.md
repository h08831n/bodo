# قوانین ثابت ایجنت (`docs/rules.md`)

> این قوانین در تمام مرحله‌ها معتبرند. اگر چیزی با مستند فنی مرحله تناقض داشت، **مستند فنی مرحله** برنده است و تناقض باید گزارش شود.
> تغییر این قوانین فقط با تایید صریح مالک پروژه (و ثبت ADR) مجاز است.

---

## ۱. منبع حقیقت و اولویت

1. مستند فنی مرحله‌ی جاری (`docs/stage-N-technical-spec.md`)
2. این فایل (`docs/rules.md`)
3. `docs/roadmap.md` (تصمیم‌های کلی و مرحله‌بندی)
4. ADRهای `docs/decisions/`

قواعد رفتاری:

- **حدس نزن.** اگر چیزی در مستندها نیست یا مبهم است، همان‌جا متوقف شو و یک سوال دقیق همراه با پیشنهاد خودت بپرس.
- **از محدوده‌ی گام بیرون نرو.** چیزی که در گام جاری تعریف نشده ساخته نمی‌شود، حتی اگر «مفید» باشد. ایده‌های اضافه را در گزارش پایان گام بنویس.
- **کتابخانه‌ی جدید** (خارج از فهرست مستند) فقط با ADR کوتاه و تایید مالک اضافه می‌شود.
- هر تصمیم فنی مهم جدید در `docs/decisions/ADR-XXXX-title.md` ثبت می‌شود (زمینه، تصمیم، جایگزین‌ها، پیامدها).

---

## ۲. روش کار (Workflow)

- **هر بار فقط یک گام** (مثلاً S1.3). گام بعدی فقط وقتی شروع می‌شود که مالک صریحاً بگوید.
- برای هر گام یک شاخه: `step/s1-3-tenancy-infra`. کامیت‌های کوچک و معنادار با قالب Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `refactor:`).
- هر گام با **Pull Request** به `main` بسته می‌شود؛ شرح PR شامل: خلاصه، چک‌لیست پذیرش، نحوه‌ی تست دستی، ADRهای جدید، موارد باقی‌مانده.
- بعد از تایید مالک و merge، tag زده می‌شود: `s1.3-done`.
- **هیچ‌وقت** مستقیم روی `main` کامیت نکن، تست را برای سبز شدن CI غیرفعال یا حذف نکن، و مایگریشن اعمال‌شده را ویرایش نکن.
- پایان هر گام: **گزارش پایان گام** با قالب بند ۱۱ ارائه شود و منتظر تایید بمان. گزارش پایان گام فقط وقتی معتبر است که لینک اجرای CI سبز همان PR در آن آمده باشد؛ اگر CI هنوز در جریان است، منتظر بمان و بعد گزارش بده.

## ۳. معماری و ایزولاسیون

- **هر شرکت یک دیتابیس مستقل است.** هیچ `company_id`، RLS یا دیتابیس مرکزی با داده‌ی کسب‌وکار/کاربر وجود ندارد.
- ممنوع: `new PrismaClient()` خارج از `TenantClientManager`. همه‌ی دسترسی به دیتابیس شرکت از `TenantContext` (AsyncLocalStorage) می‌گذرد.
- ممنوع: هر کوئری یا کدی که بین دو دیتابیس شرکت داده جابه‌جا کند، به‌جز عملیات Database Manager (کپی/بکاپ/بازیابی).
- کلیدهای Redis، نام صف‌ها، مسیر فایل‌ها و کش‌ها **همیشه با نام دیتابیس** پیشوند می‌گیرند.
- Worker و زمان‌بندها فقط از طریق `TenantRunner` روی دیتابیس‌ها می‌چرخند و خطای یک دیتابیس بقیه را متوقف نمی‌کند.
- **ساختار ماژول** طبق بند ۹ مستند فنی: controller ← service ← repository. controller منطق ندارد، service مستقیم Prisma نمی‌خواند.
- **ماژول‌ها هم‌دیگر را import نمی‌کنند**؛ ارتباط فقط از طریق service عمومی export‌شده یا **رویداد دامنه‌ای (Outbox)**. import کردن repository ماژول دیگر ممنوع است.
- هر ماژول مجوزهای خودش را با `registerPermissions` و رویدادهای timeline خودش را با `registerTimelineEvent` ثبت می‌کند.
- کاتالوگ مجوزها فقط در کد است؛ جدول Permission وجود ندارد.

## ۴. داده و دیتابیس

- هر جدول: `id` (UUIDv7 تولیدشده در اپلیکیشن)، `created_at/by`، `updated_at/by`؛ soft delete فقط در صورت نیاز؛ اسناد دارای `version` (قفل خوش‌بینانه).
- نام‌گذاری: جدول `snake_case` جمع، ستون `snake_case`، فیلد Prisma `camelCase` با `@map/@@map`.
- **مایگریشن فقط SQL دستی‌ریویوشده است.** `prisma migrate dev` فقط برای تولید پیش‌نویس است و خروجی باید بازبینی و در صورت لزوم اصلاح شود. مایگریشن اعمال‌شده هرگز ویرایش نمی‌شود؛ تغییر = مایگریشن جدید.
- مایگریشن‌ها باید روی دیتابیس خالی از صفر اجرا شوند و روی دیتابیس دارای داده‌ی نمونه هم سالم بمانند.
- همه‌ی نوشتن‌های چندمرحله‌ای در **تراکنش**؛ ثبت outbox در همان تراکنش.
- لیست‌ها **Cursor pagination**؛ `offset` ممنوع. `count` فقط با درخواست صریح (`withTotal`).
- کوئری‌های گزارشی و سنگین با `$queryRaw`/TypedSQL و ایندکس مناسب؛ هر ایندکس جدید توجیه دارد.
- جدول‌های رشدکننده (`audit_logs`، `timeline_events`) پارتیشن زمانی دارند و Prisma آن‌ها را نمی‌سازد.

### ارز و مبلغ

- مبلغ همیشه `Decimal` (هرگز `float/number` برای پول در دیتابیس یا محاسبه). در JSON، مبلغ به‌صورت **رشته**ی decimal منتقل می‌شود.
- هر سند ارز خودش را دارد و مبالغش به همان ارز است. **هیچ تبدیل، نرخ یا معادل‌سازی ارزی ساخته نمی‌شود.** هیچ جمعی بین دو ارز مختلف انجام نمی‌شود.
- ورود/نمایش مبلغ فقط با `MoneyInput` و `formatMoney(amount, currencyCode)`.

### تاریخ و زمان

- دیتابیس و API همیشه UTC/ISO-8601. تقویم شمسی **فقط** در لایه‌ی نمایش و ورودی (`packages/utils/jalali` و `JalaliDatePicker`).
- هیچ منطق کسب‌وکاری بر پایه‌ی تاریخ شمسی نوشته نمی‌شود، مگر شماره‌گذاری اسناد و گزارش‌های سال/ماه شمسی که صراحتاً در مستند آمده‌اند و از توابع مشترک استفاده می‌کنند.

### فارسی

- نرمال‌سازی فارسی/عربی (ی/ي، ک/ك، ارقام فارسی/عربی/انگلیسی، نیم‌فاصله) قبل از ذخیره‌ی فیلدهای جستجویی و در جستجو، فقط از `packages/utils`.
- اعتبارسنجی‌های ایرانی (کد ملی، شناسه ملی، کدپستی، موبایل، کد اقتصادی) فقط از `packages/utils` و با تست.

## ۵. API

- هر endpoint با **شِمای zod در `packages/contracts`** تعریف می‌شود؛ تایپ‌های بک‌اند و فرانت از همان می‌آیند. تعریف تایپ دستی تکراری ممنوع.
- پیشوند `/v1`؛ مستندات OpenAPI خودکار.
- قالب خطا و کدهای خطا دقیقاً طبق بند ۸.۱ مستند فنی؛ پیام‌ها فارسی و قابل‌نمایش به کاربر.
- هر endpoint محافظت‌شده: `JwtAuthGuard` + `UserTypeGuard` + `PermissionGuard`؛ و در صورت لزوم Record Rule. endpoint بدون گارد فقط با ذکر صریح در مستند (مثل login).
- POSTهای حساس از `Idempotency-Key` پشتیبانی می‌کنند.
- پاسخ‌ها هرگز رمز، هش، توکن یا فیلد داخلی را برنمی‌گردانند.

---

## ۶. امنیت

- هیچ رازی (رمز، کلید، توکن) در git نیست؛ فقط `.env.example` با مقادیر نمونه.
- رمز عبور: argon2id. توکن‌ها: طبق بند ۶ مستند فنی (refresh چرخشی با تشخیص استفاده‌ی مجدد).
- اطلاعات اتصال SMS/SMTP در دیتابیس با AES-GCM رمزگذاری می‌شود (کلید در env).
- لاگ‌ها هرگز رمز، توکن، کد ملی کامل یا شماره‌ی کامل کارت را نمی‌نویسند (redaction مرکزی).
- ورودی کاربر **همیشه** با zod اعتبارسنجی می‌شود؛ SQL خام فقط با پارامتر (هرگز concatenate).
- فایل‌های آپلودی: بررسی نوع و حجم، نام تصادفی، خارج از مسیر عمومی.
- Database Manager فقط با master password، قابل‌خاموش‌شدن و محدود به IP مجاز؛ همه‌ی عملیاتش در لاگ فایل ثبت می‌شود.

## ۷. فرانت‌اند

- **هیچ صفحه‌ای بدون کامپوننت‌های `packages/ui` ساخته نمی‌شود.** اگر کامپوننتی نبود: اول در `packages/ui` ساخته و در Storybook مستند شود، بعد استفاده شود. کامپوننت مخصوص ماژول فقط از ترکیب کامپوننت‌های ui ساخته می‌شود.
- تمام کامپوننت‌ها: TypeScript strict، **RTL-safe** (فقط کلاس‌های منطقی `ms-/me-/ps-/pe-/start/end`؛ استفاده از `left/right/ml/mr` ممنوع)، **ریسپانسیو موبایل‌فرست**، قابل‌دسترسی (کیبورد، ARIA)، حالت تیره، بدون وابستگی به API.
- متن‌های رابط کاربری در یک کاتالوگ مرکزی (`fa.ts`) نگه‌داری می‌شوند، نه پراکنده در JSX. کلیدها انگلیسی، مقادیر فارسی.
- داده‌ی سرور فقط با TanStack Query؛ فرم‌ها با React Hook Form + zod از `contracts`.
- مسیرها و منوها از طریق `module.manifest.ts` هر feature ثبت می‌شوند؛ نمایش بر اساس مجوز (`<Can>`).
- **هیچ وابستگی runtime به اینترنت بیرونی نیست** (CDN، فونت گوگل، آنالیتیکس، سرویس تصویر). فونت وزیرمتن و تمام asset‌ها خودمیزبان هستند، چون سرور ممکن است ایزوله باشد.
- **متن ترکیبی فارسی و انگلیسی/عدد** (کد سند، نام انگلیسی، شماره) همیشه با کامپوننت `LtrText` (`<bdi>` / `unicode-bidi: isolate`) نمایش داده شود تا جهت متن به‌هم نریزد (پیاده‌سازی کامپوننت در S1.11).
- service worker هرگز پاسخ API را cache نمی‌کند.
- کنسول مرورگر در حالت عادی بدون خطا و warning باشد.

## ۸. کیفیت کد

- TypeScript `strict`؛ `any` ممنوع (در صورت ضرورت، با `// reason:` و محدود). `@ts-ignore` ممنوع؛ `@ts-expect-error` فقط با توضیح.
- شناسه‌های کد، کامنت‌ها، نام شاخه و پیام کامیت **انگلیسی**؛ متن‌های کاربر و پیام‌های خطای نمایشی **فارسی**.
- ESLint و Prettier بدون هشدار؛ import مرتب؛ بدون dead code و بدون `console.log` (فقط logger).
- توابع کوتاه و تک‌منظوره؛ منطق تکراری در `packages/utils` یا کامپوننت مشترک.
- هیچ عدد/رشته‌ی جادویی؛ ثابت‌ها نام‌دار و در یک محل.

## ۹. تست

- هر گام همراه تست است؛ **گام بدون تست بسته نمی‌شود.**
- **Unit:** منطق service و توابع utils.
- **Integration:** با PostgreSQL واقعی (Testcontainers). دیتابیس mock نمی‌شود.
- **ایزولاسیون چنددیتابیسی، دسترسی (PermissionGuard/Record Rule)، Provisioning، بکاپ/بازیابی و مایگریشن چندگانه:** تست اجباری طبق بند ۱۲ مستند فنی.
- **Contract:** هر endpoint در برابر شِمای zod.
- **e2e (Playwright):** فقط جریان‌های اصلی هر گام.
- **تست مسیر منفی و ارورهای کاربرمحور:** هر ابزار کاربرمحور (CLI، لانچر، endpoint) باید مسیر منفی هم تست شود و خروجی خطایش قابل‌فهم و فارسی/انگلیسی خوانا باشد؛ 500 برای ورودی نامعتبر یک باگ است.
- تست‌های flaky باید همان لحظه اصلاح شوند، نه skip.
- CI روی هر PR: lint + typecheck + test + build + اجرای مایگریشن روی دیتابیس خالی.

## ۱۰. محیط توسعه (ویندوز)

مالک پروژه روی **Windows (PowerShell)** کار می‌کند؛ پس:

- اسکریپت‌های `package.json` و ابزارها **cross-platform** باشند (بدون دستورهای مخصوص bash). برای کارهای پیچیده Node script یا `tsx`.
- پایان خط فایل‌ها LF؛ `.gitattributes` و `.editorconfig` الزامی است.
- Postgres و Redis با Docker Desktop (`docker compose`). مسیر ابزارهای `pg_dump/pg_restore/psql` با `PG_BIN_PATH` قابل‌تنظیم باشد و در image تولید نسخه‌ی ۱۶ نصب باشد.
- هر سرویس یا وابستگی جدید (مثلاً MinIO) باید در همان گامی که اضافه می‌شود، به اسکریپت‌های start/stop/status ویندوز هم اضافه شود.
- مسیرها با `path.join` ساخته شوند (نه رشته‌ی `/` ثابت).
- README باید دستورهای دقیق PowerShell را برای راه‌اندازی داشته باشد.
